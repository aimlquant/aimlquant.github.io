“사용법”보다 중요한 것은 작업 순서입니다

코딩 에이전트에게 한 문장으로 맡길 수는 있지만, 좋은 결과는 한 번의 생성보다 각 단계의 입력과 완료 기준을 분리할 때 나옵니다. 사람은 방향과 공개 여부를 결정하고, 에이전트는 감사·생성·검증·반복 수정의 증거를 남깁니다.

가장 짧은 요청

“이번 주 ○○ 스터디 Chapter ○ 발표자입니다. 프로젝트 스킬을 사용해 원자료를 감사하고, 상세 리포트를 먼저 완성한 뒤 발표자료를 만들어 주세요. 검증 결과와 로컬 확인 URL을 보고하고, 배포는 제가 요청할 때만 하세요.”

에이전트가 맡는 일

파일·좌표 인벤토리, 환경 준비, 골격 생성, 코드 실행, 리포트/덱 제작, 자동 검증, 실제 렌더 캡처, 링크 점검입니다.

사람이 결정하는 일

설명의 깊이와 취향, 원자료 매핑의 애매함, 라이선스 동의, 민감정보 판정, 최종 공개·배포 승인입니다.

REPOSITORY MODEL

원자료와 공개 산출물을 분리합니다

영상에서 두 저장소를 함께 클론한 이유입니다. 작업용 원자료와 공개 가능한 결과물은 권리·보안·배포 방식이 다르므로 같은 저장소에 섞지 않습니다.

Private workspace

aimlquant/study-materials

원문, 번역·해설, 업스트림 코드, 데이터 매니페스트, 실행 노트북을 준비하는 곳입니다. 참가 권한이 있어야 접근할 수 있습니다.

Public output

aimlquant/study

상세 리포트, 발표 덱, 회차 페이지와 공용 생성·검증 도구를 관리합니다. html/의 검증된 결과만 Pages에 공개합니다.

공개 경계

책 그림·표 스캔, 비공개 원문, API 키, 쿠키, 로컬 절대경로를 public 저장소로 옮기지 않습니다. 공개 도형은 의미를 보존한 자체 재구성을 기본으로 하고, 원본 코드의 공개 라이선스가 책 본문·그림의 공개 권리까지 뜻하지는 않습니다.

PROJECT SKILLS

무엇을 만들지에 따라 스킬을 고릅니다

스킬 이름을 프롬프트에 직접 적어도 되고, 아래 목적을 분명히 쓰면 에이전트가 해당 절차를 선택합니다. 여러 스킬이 필요하면 표의 위에서 아래 순서로 진행하는 것이 안전합니다.

study-materials

교재 코드·데이터·해설 노트북

새 교재 환경을 만들거나 챕터 소스를 배치하고, 실행 가능한 학습 노트북을 준비할 때 사용합니다.

  • 입력: study.toml, 원문·해설, 업스트림 코드
  • 출력: 챕터 src/, 실행 노트북, coverage·검증 결과
  • 핵심: 챕터·리스팅 매핑을 개수로 추측하지 않기
study-presentation

상세 리포트와 발표 덱

발표 회차의 원자료를 감사하고 장문 리포트를 먼저 완성한 뒤, 그 근거만으로 발표자료를 만들 때 사용합니다.

  • 입력: 해설·노트북·원문 좌표 감사표
  • 출력: report.html, index.html, 재구성 도형
  • 핵심: 리포트 게이트 전에는 덱 본문으로 넘어가지 않기
localize-image-text

그림 안 영문을 한국어로

PNG/JPEG의 구조와 화살표를 유지하면서 라벨만 번역해야 할 때 사용합니다. 생성형 편집 대신 마스크·타이포 합성을 사용합니다.

  • 원본은 보존하고 한국어 PNG와 재현 가능한 spec을 별도 저장
  • ID·코드·URL·속성 키는 원칙적으로 보존
  • 원본 크기와 실제 문서 표시 크기를 모두 육안 검수
study-operations

회차 등록·Pages·공개 영상 연결

자료가 완성된 뒤 회차 레지스트리, 공개 페이지, YouTube 링크를 연결하고 배포 상태를 검증할 때 사용합니다.

  • 자료 URL을 먼저 만들고 공개 영상만 역연결
  • private/unlisted 영상 ID는 공개 저장소에 기록하지 않기
  • Actions 성공뿐 아니라 실제 공개 딥링크까지 확인
create-chan-chapter-analysis · 선택 경로

Ernest P. Chan 교재의 재현 실험

Machine Trading처럼 Chan 교재의 백테스트·수치 실험을 구현할 때만 추가합니다. 공식 데이터 출처와 해시, 수식-코드 대응, 책 결과와 Python 결과의 허용오차, 편향·거래비용·out-of-sample 한계를 한 묶음으로 검증합니다. 일반 개념 장이나 발표 HTML만 만드는 작업에는 필요하지 않습니다.

STEP-BY-STEP

실제 작업은 일곱 단계로 끊습니다

각 카드의 “완료 기준”을 통과한 산출물만 다음 단계의 입력으로 사용합니다.

01
Scope & baseline

회차와 현재 상태부터 확정

날짜, 스터디, 챕터, 발표자, 발표 시간을 확인하고 두 저장소의 변경 상태와 기존 회차 폴더를 먼저 봅니다.

  • studies.toml에서 현재 materials 경로 확인
  • 기존 변경·기존 산출물을 덮어쓰지 않기
  • private 저장소 접근과 SSH 인증 확인
  • 기존 검증 실패가 있으면 먼저 원인 분리
완료 기준: 대상 회차와 입력 경로가 한 가지로 확정되고, 기존 변경의 소유 범위를 설명할 수 있다.
02
Learning foundation

해설·코드·노트북을 실행 가능한 상태로 준비

원문을 바로 발표 HTML로 바꾸지 않습니다. 먼저 해설판과 챕터 코드를 정리하고, 필요한 경우 환경과 노트북을 재현합니다.

  • 교재의 고정 Python 버전과 챕터별 의존성 유지
  • 책 챕터와 업스트림 폴더를 고유 키워드로 대조
  • 모든 Listing을 실행·대체·문서화·선택 실행으로 분류
  • 실측값과 책 값을 구분하고 데이터 드리프트 설명
완료 기준: 기본 verification gate가 통과하고, 코드가 있는 챕터의 노트북은 오류 없이 읽고 실행할 수 있다.
03
Source inventory

원자료의 학습 좌표를 전수 감사

장·절 순서뿐 아니라 그림, 표, Listing, Example, Box, 연습문제와 각 주장에 붙은 조건·귀속·한계를 기록합니다.

  • 정확한 번역 제목과 등장 순서 유지
  • 정의·메커니즘·근거/예시·실패 경계 수집
  • 출처의 조건부 주장을 보편 사실로 높이지 않기
  • 공개 재구성이 필요한 시각 관계 표시
완료 기준: 원자료의 모든 핵심 좌표가 “어디에서, 무엇을, 어떤 강도로 말하는지” 추적된다.
04
Report gate

상세 리포트를 먼저 읽을 만하게 완성

첫 결과는 대개 틀입니다. 절 누락, 지나치게 짧은 설명, 반복 그림, 부자연스러운 번역을 원자료와 대조해 반복 수정합니다.

  • 원본 절마다 정의와 작동 방식, 예시 또는 한계 제공
  • 그림은 읽는 법·의미·적용 경계를 캡션에 설명
  • 새 운영 제안은 “AIML Quant 보충”으로 분리
  • 데스크톱·모바일·A4에서 실제 렌더 확인
완료 기준: 원자료 없이도 리포트만으로 흐름을 이해할 수 있고, 모든 주요 절·표·그림의 근거가 추적된다.
05
Report-derived deck

리포트의 논리를 발표 밀도로 압축

슬라이드에서 새 주장을 만들지 않습니다. 새 근거가 필요하면 리포트를 먼저 고치고 다시 게이트를 통과합니다.

  • 50분 발표는 보통 18–30장, 필요하면 근거 커버리지 우선
  • 한 슬라이드에 의미 있는 그림 하나를 기본으로
  • 그림 읽는 법·필요성·실패 경계를 세 문장 안으로
  • 1600×900, 1366×768, 390px에서 실제 픽셀 검수
완료 기준: 모든 슬라이드가 리포트 근거로 연결되고, 기본 발표 화면에서 글자·도형·코드가 읽힌다.
06
Verification

자동 검사와 사람의 시각 감사를 함께 통과

명령 성공만으로 완료하지 않습니다. 생성 결과의 링크와 구조를 검사한 뒤, 보호된 브라우저 러너로 실제 화면을 열어 봅니다.

  • 테스트·site build·check·validate·diff check 실행
  • 텍스트 잘림, 그림 과소/과대, 화살표 오착지 확인
  • 한 결함을 찾으면 같은 레이아웃의 형제도 전수 감사
  • 민감정보, 로컬 URL, 공개 권리와 링크 재확인
완료 기준: 자동 검증 0 오류와 실제 렌더 검수가 모두 끝나고, 미검증 viewport가 없다.
07
Publish & handoff

명시적 요청 뒤 배포하고 공개 URL을 다시 확인

commit·push·Pages 변경은 사용자가 요청했을 때만 합니다. Actions 성공 뒤에도 같은 head SHA의 실제 딥링크를 데스크톱·모바일에서 확인합니다.

  • 회차 URL과 자료 링크를 먼저 고정
  • 영상은 실제 public이 된 뒤에만 역연결
  • 중단 시 완료·미완료·다음 명령을 핸드오프에 기록
  • 다음 세션은 처음부터 만들지 말고 기록에서 재개
완료 기준: 배포 commit, Pages run, 공개 페이지의 내용·영상·링크가 서로 일치한다.

COPY-READY PROMPTS

상황에 맞게 복사해서 쓰는 프롬프트

꺾쇠 부분만 실제 값으로 바꾸면 됩니다. 처음부터 배포 권한까지 주고 싶지 않다면 “배포하지 말 것”을 꼭 남깁니다.

1. 처음부터 자료 패키지 만들기교재 준비 → 리포트 → 덱
이번 주 발표 회차는 <YYYY-MM-DD>, <스터디 이름>의 <Chapter N>이고 발표자는 <이름>이다.

study-materials와 study-presentation 스킬을 이 순서로 사용해라.
1. studies.toml과 교재 study.toml로 실제 경로를 확정하고 기존 변경을 보존해라.
2. 원문·번역·해설·노트북·코드에서 절, 그림, 표, Listing, Example, Box, 연습문제를 원본 순서로 감사해라.
3. 코드가 있으면 실행 환경과 listing coverage를 검증하고, 실행하지 못한 것은 이유와 요구 조건을 남겨라.
4. 상세 리포트를 먼저 완성하고 데스크톱·모바일·A4 리포트 게이트를 통과해라.
5. 승인된 리포트만 근거로 발표 덱을 만들고 1600×900, 1366×768, 390px에서 실제 렌더를 검사해라.
6. 자동 검증 결과, 변경 파일, 로컬 확인 URL, 사람이 판단할 항목을 보고해라.

commit, push, Pages 배포는 하지 마라.
2. 초안의 품질을 올리기첫 결과를 그대로 쓰지 않기
<report.html 또는 공개/로컬 URL>의 품질을 원자료와 대조해 개선해라.

study-presentation 스킬을 사용하고 다음 순서로 진행해라.
- 원자료 감사표와 현재 리포트의 절·그림·표·코드 커버리지를 비교한다.
- 제목만 있고 설명이 빈 절, 정의 없는 전문 용어, 지나치게 짧은 설명, 누락된 조건·귀속·실패 경계를 찾는다.
- 반복 그림, 잘못된 그림 위치, SVG 텍스트 넘침, 화살표 오착지와 같은 결함을 형제 그림 전체에서 함께 고친다.
- 슬라이드에만 있는 새 주장은 리포트에 먼저 반영한다.
- 변경 후 리포트와 연결된 모든 슬라이드를 다시 감사하고 실제 크기로 렌더한다.

무엇을 왜 바꿨는지와 아직 사람이 판단해야 할 부분을 요약해라. 배포는 하지 마라.
3. 오류를 진단하고 고치기증상·재현 명령·기대 결과 제공
다음 스터디 자료 작업의 오류를 진단하고 수정해라.

대상: <교재/회차/파일 경로>
증상: <무엇이 보이거나 실패하는가>
재현 명령: <실행한 명령>
마지막 오류: <핵심 로그>
기대 결과: <원하는 상태>

관련 프로젝트 스킬과 AGENTS.md를 먼저 읽고, 기존 사용자 변경을 보존해라.
원인을 증거로 설명한 뒤 가장 작은 수정으로 고치고, 같은 결함이 있을 수 있는 형제 파일도 감사해라.
검증 규칙을 약화하거나 실패를 건너뛰지 말고, 수정 후 원래 실패 명령과 전체 게이트를 모두 다시 실행해라.
외부 라이선스 동의나 공개 승인이 필요하면 그 지점에서 멈추고 명확히 보고해라.
4. 검토가 끝난 자료 배포하기명시적으로 공개를 요청할 때
<회차 또는 가이드 경로>의 검토가 끝났다. study-operations 스킬로 배포해라.

- 현재 diff에 비공개 원문, 책 그림·표 스캔, API 키, 쿠키, 사설 IP, 로컬 절대경로가 없는지 확인한다.
- 필수 unittest, build_site, build_site --check, validate-site, git diff --check를 실행한다.
- 관련 변경만 commit하고 main에 push한다.
- Pages 실행의 head SHA가 방금 push한 commit과 같은지 확인하고 배포 완료를 기다린다.
- 캐시 우회 query를 붙인 실제 공개 딥링크를 데스크톱·모바일에서 렌더해 내용·링크·16:9 영상 프레임을 확인한다.
- 최종 commit, 검증 결과, 공개 URL을 보고한다.
5. 세션을 중단하고 이어서 하기긴 작업의 핸드오프
현재 작업을 처음부터 다시 하지 않고 이어갈 수 있도록 핸드오프를 작성해라.

- 목표와 사용 중인 프로젝트 스킬
- 완료한 단계와 검증 증거
- 변경한 파일과 사용자 변경으로 보존해야 할 파일
- 실패한 시도, 원인, 다시 하면 안 되는 명령
- 현재 실행 중인 프로세스와 안전 제한
- 남은 단계를 실행 순서대로 적은 정확한 명령
- commit/push/공개 여부와 아직 필요한 사용자 승인

새 세션에서는 이 핸드오프와 git status를 먼저 읽고 남은 첫 단계부터 재개하게 해라.
자주 쓰는 검증 명령꺾쇠 값은 registry 기준으로 교체
# study와 study-materials가 나란히 있을 때, study 저장소에서 논리 경로 연결

TROUBLESHOOTING

막히는 지점은 대부분 정해져 있습니다

증상을 펼치면 먼저 확인할 근거와 안전한 해결 순서를 볼 수 있습니다.

private study-materials가 clone되지 않습니다

확인: GitHub 웹에서 저장소가 보이는지 먼저 봅니다. 보이면 팀 권한보다 로컬 인증 문제일 가능성이 큽니다.

조치: 현재 계정의 public SSH key가 GitHub에 등록됐는지, 터미널의 ssh-agent가 키를 읽는지 확인한 뒤 같은 clone URL로 재시도합니다. 키나 토큰을 채팅·저장소에 붙이지 않습니다.

환경 설치 중 Python·패키지 버전이 충돌합니다

원인: 교재와 챕터마다 검증된 버전이 다를 수 있습니다. 최신 Python으로 임의 업그레이드하면 휠이 없어 빌드가 깨지기도 합니다.

조치: study.toml의 Python 버전을 유지하고 setup_env.py를 다시 실행합니다. 챕터가 바뀌면 그 챕터의 tasks.py init을 사용하고, 정말 충돌하면 챕터 전용 환경을 검토합니다.

챕터와 업스트림 소스가 맞지 않습니다

원인: MEAP와 최종판의 챕터 번호, Listing 번호가 어긋날 수 있습니다.

조치: 폴더 수나 제목 인상으로 짝짓지 말고 원문 고유 키워드와 실제 Listing 제목·심볼을 대조합니다. 확정 결과는 study.toml의 mapping에 기록하고, 최종판에 없는 소스는 meap-only/로 분리합니다.

Neo4j 또는 외부 서비스가 실행되지 않습니다

확인: 챕터가 Community + n10s, Enterprise 기능, 또는 GDS 중 무엇을 요구하는지 확인합니다. 이 조합은 서로 호환되지 않을 수 있습니다.

조치: 챕터 요구에 맞춰 컨테이너를 분리합니다. Enterprise 평가 라이선스는 사용자가 직접 읽고 동의해야 하며 에이전트가 대신 수락하지 않습니다. 개인 API 키가 없으면 해당 Listing은 documented-only로 남깁니다.

LLM 호출이 unknown provider/model로 실패합니다

원인: 업스트림 Listing이 현재 프록시에서 제공하지 않는 모델명을 하드코딩했을 수 있습니다.

조치: study.toml의 외부 env_file을 사용하고 비밀값을 복사하지 않습니다. 업스트림 파일을 고치는 대신 임포트 뒤 런타임 모델 override를 사용하고, 실제 모델·시점·조건을 노트북에 기록합니다.

검증은 통과했는데 노트북이 완성되지 않았습니다

원인: status = draft인 노트북에 --lint만 실행하면 구조 검사만 통과할 수 있습니다.

조치: 모든 TODO(agent)를 없애고 책 Listing 전부의 coverage를 선언한 뒤 status = complete로 바꾸고 기본 verification gate와 필요한 경우 --execute를 실행합니다.

그림 URL은 200인데 노트북이나 HTML에 보이지 않습니다

원인: 뷰어가 remote image를 제거하거나 상대경로를 해석하지 못할 수 있습니다.

조치: 노트북 그림은 attachment로 내장합니다. 자동 그림 매핑은 캡션 위치를 잘못 잡을 수 있으므로 원문 캡션과 실제 이미지를 눈으로 대조합니다. HTML/SVG는 최종 표시 크기에서 다시 렌더합니다.

상세 리포트가 너무 짧고 일반적인 요약처럼 보입니다

원인: 첫 생성본의 카드와 제목을 완성본으로 취급했기 때문입니다.

조치: 원자료 감사표로 돌아가 절별 정의, 작동 방식, 근거·예시, 조건·실패 경계를 채웁니다. 중복 그림과 누락 좌표를 찾고 자연스럽지 않은 번역을 고친 뒤 리포트 게이트를 다시 통과합니다.

SVG 화살표·텍스트가 어긋나거나 슬라이드에서 작게 보입니다

조치: 소스 좌표가 아니라 최종 표시 크기의 픽셀을 봅니다. 같은 수준의 박스를 공통 그리드에 맞추고 화살표 끝을 의도한 면의 경계에 붙입니다. marker-end path에는 fill:none을 명시하고, 같은 패턴의 형제 도형을 전부 다시 렌더합니다. 확대 기능은 기본 가독성의 대체가 아닙니다.

로컬에서는 보이는데 GitHub Pages가 갱신되지 않습니다

확인: build가 만든 변경까지 commit됐는지, push한 branch와 Pages run의 head SHA가 같은지 확인합니다.

조치: build/check/validate를 다시 실행하고 관련 파일만 commit·push합니다. Actions 성공 뒤 캐시 우회 query를 붙인 정확한 공개 딥링크를 열어 실제 내용을 확인합니다.

에이전트 세션이 중간에 끊겼습니다

조치: 처음부터 다시 생성하지 않습니다. git status, 마지막 검증 로그, 핸드오프의 완료·미완료 목록과 금지 명령을 읽고 다음 한 단계부터 재개합니다. 실행 중이던 무거운 프로세스가 있다면 자원 제한과 임시 파일 상태를 먼저 확인합니다.

자동 승인 모드는 품질 게이트를 없애지 않습니다.

영상에는 빠른 시연을 위해 먼저 배포하는 장면도 있지만, 권장 절차는 리포트를 읽을 만하게 만든 뒤 덱과 공개로 넘어가는 것입니다. 에이전트의 자율 실행 범위와 commit·push·공개 권한은 별개의 결정입니다.
